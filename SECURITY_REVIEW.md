# Security review

## Implemented controls

The CMS uses Node core HTTP, crypto, zlib and SQLite. The production application has no third-party npm dependencies. SQLite uses bound parameters, foreign keys, write-ahead logging, FULL synchronous mode and immediate transactions for related writes. The service creates the database with restricted local permissions. Run it under its own unprivileged OS account on a private persistent volume. Runtime image and operating-system updates remain an operator responsibility.

* The first owner is created only from the host using `node cms/owner.mjs USERNAME` and a passphrase on standard input. The command refuses a second bootstrap. No default credentials or public registration exist.
* Passwords use independently salted scrypt with N=32768, r=8, p=1 and a timing-safe comparison. Unknown usernames incur a dummy hash calculation. Inputs must be at least 14 characters and at most 256 UTF-8 bytes. Passwords and hashes are excluded from activity log entries. Require unique passphrases and a private admin network or identity-aware proxy for launch. Native MFA is not implemented.
* Sessions use 256-bit random tokens, with SHA-256 digests at rest, an eight-hour absolute lifetime, HttpOnly, SameSite=Strict and Secure with a __Host- prefix on HTTPS. HTTP is accepted only for a configured loopback origin. Administrative writes require an exact Origin match. Authenticated writes additionally require a session-bound CSRF token. Logout, password rotation, deactivation and role changes revoke applicable sessions; the server checks authorization again after asynchronous processing.
* Login attempts are rate limited per immediate TCP peer to 16 in 15 minutes, and administrative writes to 180 per minute per user. The application intentionally ignores unsanitized forwarded IP headers. Shared proxy clients share this limit. Configure edge filtering and proxy/CDN authentication at deployment.
* OWNER manages accounts and publication. CONTENT_MANAGER edits content except business settings and can immediately hide products. VIEWER reads records. Only owners can access the account administration and audit areas. An owner cannot disable or demote their own account.
* Publication requires explicit confirmation of source, verification date, rights and final applicable prices. Public data reads only the live copy. Revision checks and transactional audit events preserve the old live copy during editing and prevent stale-tab overwrites.
* Input is validated on the server. UI strings and stored text are HTML-escaped. Admin pages disallow executable scripts through CSP, deny framing, restrict forms to the same origin and send no-store and noindex directives. Route handlers apply role checks independent of visibility of controls.
* Stored uploads accept bounded noninterlaced eight-bit RGB/RGBA PNG only. The parser validates signature, chunks and CRCs, checks image dimensions and scanline data, caps decompression at the expected size and writes newly constructed critical PNG chunks. No filename is interpreted as a path. Draft image access requires authentication. Audited uploads and published data share the backed-up SQLite database.
* The public contact form is disabled and does not collect messages. No external trackers are activated by the CMS. Administrators generate account, activity, source and revision data. Login limiting stores a digest of the immediate peer address during its window. Expired limit/session records are purged during further authentication or mutation traffic. New sessions cannot use an expired row.

## Verification and remaining operational work

Run `node --test tests/cms.test.mjs` from the project root. The suite creates a disposable SQLite file, boots a real HTTP server, signs in, edits records through ordinary form endpoints, checks actual publication, uploads a generated PNG and verifies session revocation. Its malformed-price fixture exercises only the temporary test database. See `QA_RESULTS.md` for run-level evidence.

Before opening the site, the operator must configure canonical HTTPS origin, restrict staging access, create owner credentials via a secure terminal, encrypt disks and backups, demonstrate restoration and restrict access to audit data. Choose a documented retention period for audit history, accounts and backups and supply an owner privacy rights channel. No unattended retention job deletes immutable revision evidence. The service is intended for one persistent host. Do not place the SQLite volume on ephemeral serverless storage or expose a backup publicly. Neither the source review nor these tests certify PDPL compliance or prove absence of defects.
